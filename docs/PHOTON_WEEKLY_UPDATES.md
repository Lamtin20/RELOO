# Photon Vietnam weekly refresh

Implementation prepared; production timer activation and Docker end-to-end verification are NOT_TESTED. This is a data refresh only, not a software updater or a claim that all upstream places are current.

## Schedule and behavior

`deploy/systemd/reloo-photon-update.timer`: Monday **00:00 Asia/Ho_Chi_Minh** (Sunday 17:00 UTC), no random delay. `Persistent=true` runs a missed check after the machine returns. Actual start/completion depends on host availability, upstream availability and import duration. No new upstream checksum means no download/import/switch. The publisher's compatible `1.0-latest` Vietnam dump is checked; changes published after the check wait until the following week. Publisher availability/freshness is not guaranteed.

The updater downloads only GraphHopper's HTTPS Vietnam dump/checksum, checks publisher MD5 and records SHA256. MD5 detects download corruption; it is not an independent signature or provenance approval. Photon JAR/JRE remain digest-pinned. Import is offline, UID1000, resource-limited, in a separate release directory. The old index stays live while the candidate starts. Forward/reverse smoke checks precede and follow atomic `state/active.json` replacement. Failed validation restores the old pointer. A pending journal recovers interrupted switches on the next invocation. An exclusive host lock prevents concurrent jobs. Retention preserves current and previous datasets; cleanup only removes updater-owned releases. Cleanup errors are reported without rolling back a healthy committed index.

Requires at least 12GiB free disk and 3GiB available RAM before import; runtime import has a 2GiB free-disk floor, 90-minute timeout, 2 CPUs and 2304MiB container memory limit. These are conservative refusal thresholds, not measured production capacity guarantees. Both serving slots can briefly run alongside import. Existing business records and private addresses are never imported or modified by this job. Publisher download requests contain no RELOO search queries/GPS.

## Reviewed deployment procedure

1. Obtain current-source release gate PASS and staging acceptance. Use a dedicated root-owned `/srv/reloo-maps/photon` (not a symlink), pinned `photon-1.3.0.jar`, pinned JRE image already available, and existing `reloo-map-private` Docker network. Host requires Python3, Docker and a reviewed Python virtual environment at `/opt/reloo-photon/venv` with `zstandard==0.25.0`. No automatic package or paid-service activation is included.
2. Bootstrap in staging, then in the approved production maintenance procedure: run `python deploy/maps/photon_weekly_update.py --root /srv/reloo-maps/photon` using that environment. With no pointer, slot A is imported and verified. Do not fabricate a pointer referencing the old standalone service. Bootstrap does not change the existing backend configuration.
3. Mount `/srv/reloo-maps/photon/state:/run/reloo-photon:ro` into every backend/renderer, retain their existing networks and add `reloo-map-private`. Set `RELOO_PHOTON_ACTIVE_STATE=/run/reloo-photon/active.json`. The backend chooses only fixed private A/B hosts, reads the pointer per request, and fails closed on missing/invalid configured state. Verify real forward/reverse queries, both slots, rollback, restart and desktop/iPhone/Android runtime consistency. Retire the legacy standalone `map-geocoder` only after verification; the updater never stops it.
4. From the reviewed repository root on Linux, run `node scripts/install-photon-schedule.mjs`. It enforces the release gate, prerequisites and bootstrap, installs service/timer and enables the timer. Docker management is privileged: this fixed-purpose root job must remain operator-owned; no web endpoint can launch it or edit its configuration. Review the systemd sandbox on the deployment host.
5. Verify `systemctl status reloo-photon-update.timer`, `systemctl list-timers reloo-photon-update.timer`, and `systemd-analyze calendar 'Mon *-*-* 00:00:00 Asia/Ho_Chi_Minh'`. Inspect `journalctl -u reloo-photon-update.service`, `state/last-run.json`, active/release manifests and private API health. Configured source files alone do not prove the timer is enabled.

## Failure and rollback

`last-run.json` records RUNNING/UNCHANGED/UPDATED/FAILED and bounded error codes. The service retries failures after five minutes, limited to three starts per hour. Alert operationally on FAILED, stale RUNNING, missing next timer or no successful check for eight days; automatic external alert delivery is not configured. To retry after repairing resources/upstream: `systemctl start reloo-photon-update.service`. A crash is reconciled at the next invocation; it is not immediate automatic failover of a serving node. Preserve logs and validate application queries before declaring recovery.

For manual data rollback, stop/disable the timer, acquire the same `update.lock`, verify the previous release manifest, start its managed slot with the pinned jar/image and retained index, run health checks, then atomically replace the pointer with that manifest. Do not edit a live index or point at a stopped slot. This operator rollback procedure is NOT_TESTED on a Docker host. Rollback of the feature uses the matching previous backend/config and legacy service; keep public APIs closed if no verified service is available.
