# Precise location and landmark photos — implementation scope

## Owner revision — mandatory street and house/landmark

This revision supersedes photo/pin-confirmation requirements below: street AND house number/recognizable address are required for onboarding/profile address and new listings. House accepts descriptive text (no numeric-only constraint). The location confirmation checkbox is removed; enabling GPS and selecting/changing a pin needs no extra tick. Explicit GPS permission, accuracy/freshness checks and separate rental handover-sharing consent remain. No new entrance-photo uploads: POST returns410; legacy owner-only read/delete and account deletion cleanup remain to avoid abandoning private files. No automatic deletion of existing photos, no binding policy edit, no production deployment. Affected modules: address forms/validation, shared precise location control, retired upload API. Existing RULE-006/010/015/016/017/020 review scope applies; collection is reduced, no new provider/assets.

Owner request: location permission required before publishing/rental requests, reported GPS accuracy strictly below 20m, editable confirmed home pin, existing written address preserved, reusable private default, optional entrance photo, 3D route presentation. Scope: onboarding/profile, listing creation, rental inquiry, map picker. No automatic background GPS and no automatic photo analysis. Explicit button initiates GPS; failed/denied/poor fixes must block new location-gated actions without presenting fabricated accuracy. Browser/native GPS is client-reported and not proof against spoofing or a survey-grade guarantee. A manually corrected pin has unknown measured accuracy, regardless of the GPS permission sample.

New private data: confirmed pin lat/lng, source, consent/confirmation, recent GPS sample/accuracy/timestamp, entrance note and owner-only WebP photo reference. Purpose: reusable delivery/pickup/service reference, no public home coordinates/photos. Provider: existing self-hosted map adapters; photo processing local sharp, no new external AI. Existing approximate public listing projection must remain unchanged. Data location: private profile addressDetails and private listing location_details, owner-scoped private filesystem for photos; API gated by existing HttpOnly account/origin/rate checks. Photo capture can expose people/house numbers: user should avoid those and can remove photo; no ownership/location verification is inferred from a photo. Existing account deletion retention workflow needs review for the new private files before release.

Affected RULE-006 (explicit location/photo purposes), RULE-010 (user-provided asset provenance), RULE-015/016 (contrast/keyboard), RULE-017 (no tracking/public leakage), RULE-020 (current-source evidence), plus existing VN-DATA review. Mandatory location as a service condition and retention/deletion require NEEDS_LEGAL_REVIEW; no binding policy/approval is invented. No production activation in this implementation. Full native, device GPS accuracy, private delivery-sharing authorization, complete 3D source coverage and production runtime acceptance must be measured, never presumed.

## Implemented behavior and deployment prerequisites

`PreciseLocationField` is shared by onboarding, profile address, listing address and rental inquiry. The existing province/ward/house/street fields remain. Empty publishing forms load the saved profile address only if untouched; rental controls prefill the saved pin. Default reuse never reuses a fresh GPS permission claim. GPS requests are explicit one-shot high-accuracy calls, never started on mount. Refresh failures clear the previous fix/confirmation. Server validates range, strict accuracy, freshness, confirmation and photo ownership before new listing/inquiry writes; a GPS-sourced pin must match its GPS sample. Manual/search pins are explicitly not measured. Owner edits of existing listings and legacy address-only profiles are not retroactively erased.

The private MapLibre picker shows the exact selected pin instead of applying the public 1.6km approximation; it can show an uncertainty polygon, pitch, conditional building extrusions and driving preview with start/end markers. The preview runs only after an explicit request and uses the configured router; no live traffic is claimed. It previews the caller's GPS to chosen entrance, not an unauthorized lender's private home. A handover card in the participant-only chat displays the shared pin/instructions and offers explicit GPS-to-entrance route preview. Complete order-specific delivery tracking, exact lender pickup disclosure, all service mini-app booking integrations and multiple saved-address management are not implemented by this change.

Photos use authenticated `/api/profile/location-photo` upload and owner-bound GET/DELETE, streamed 8.2MB multipart limit, 8MB file limit, local WebP normalization (max1280px/200KB), no public media table/URL. Storage is `RELOO_PRIVATE_LOCATION_MEDIA_DIR` or `data/private-location-media`, outside public/, with owner-hashed folders and restricted modes. Provision the same private persistent directory read/write to backend and deletion worker; never expose it with a static web server/CDN. Files must participate in approved encrypted backup/retention operations. Up to10 files perowner prevent unlimited disk growth; remove unused photos. Automatic orphan expiry remains pending retention review. Photo bytes are not passed to AI/geocoding.

Existing account-deletion worker deletes only valid owner-scoped WebP filenames before completing deletion; retries fail closed for unexpected paths. No schema migration/new public grants are required: confirmed metadata fits the existing profile/listing private JSON fields, subject to existing SQL size limits. Existing database functions preserve inquiry `handoverLocation` message metadata, but production persistence/recipient display still require end-to-end acceptance. The rental inquiry sends coordinates/instructions only after a separate sharing acknowledgement; photo and raw GPS sample are omitted from that message.
