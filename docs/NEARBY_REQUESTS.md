# Nearby rental and purchase requests

Home CTA links to `/needs`. Authenticated, active accounts can create up to three requests in a rolling 24-hour window. Requests expire after seven days and can be closed by their author. One optional reference image uses the existing server WebP pipeline.

The shared browser address catalog now calls `/api/address/p/` and `/api/address/w/?province=...`. This fixed the strict CSP blocking direct browser requests to the external province catalog. The server only permits the fixed catalog paths and known province codes; it caches responses without broadening connect-src. The authenticated request overview reports whether Gmail configuration is present, and the author-only detail reports pending, sent and review delivery counts.

Member email enrollment is separate from marketing email preferences, explicit and off by default. `/needs#nearby-subscription` enrolls or disables it; opting out remains available to inactive accounts. The province is selected from the existing official-address catalog and confirmed by the user, not inferred from a province centroid. GPS coordinates are supplied with browser permission; they are not proof of residence or an authoritative province-boundary lookup. We do not silently geolocate members or import approximate historical addresses.

Backend-only location records expire from matching after 180 days. Exact coordinates and recipient identities are excluded from API detail responses and emails. PostgreSQL computes great-circle distance, enforcing <=10 km and identical province codes before selection and again before delivery. Only enrolled active members qualify. Matching compares category, rental/sale compatibility and normalized title tokens. This is approximate matching, not an AI assertion that the asset is identical. Up to 25 nearest matching owners are selected; if none qualify, up to 50 nearest enrolled community members. The same person receives at most three notices per rolling 24 hours. Missing coordinates never fall back to province centers.

`NEARBY_REQUEST_MATCH` runs through the existing operations worker. Recipient queues are transactional, locked, deduplicated by request/member, and obey opt-out and per-member caps. The worker checks Gmail configuration and drains five emails every 30 seconds. It rechecks request expiry/closure, membership, province and distance. `QUEUED -> SENDING` is conditional and atomic. SENT records keep the Gmail message ID. A send failure/timeout becomes FAILED for review, never automatic resend; a crash while SENDING likewise requires review because Gmail may already have accepted the email. This favors preventing duplicates over automatic redelivery.

Invited members can offer an available asset they own, of compatible category and transaction mode. The author receives an existing in-app/system notification, opens the product, then uses the existing secure chat/transaction workflow. A recipient without a listing is directed to `/lend` first. Request URLs require sign-in plus author/invited-recipient access. They are noindex.
