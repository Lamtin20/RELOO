# Images, Calendar onboarding, contextual headers and loading

Image generation now varies scene, framing and palette deterministically by article title and topic. Finance/environment/equipment have separate scene families instead of repeating the notebook/wallet/calculator desk. This applies to future editorial AI calls. Existing images and banners are not automatically regenerated or billed. Prompt diversity is verified; new paid image outputs have not been generated solely to test this change.

Calendar setup is offered after the first authenticated web session, reusing server onboarding preference and existing OAuth flow. Native first-launch introduction calls the actual RelooCalendar permission API only after the user taps Allow, and records dismissal locally to avoid repeated requests. Selecting a destination calendar after login is still required; permission is not a fabricated sync receipt. Android/iOS permissions can be revoked and OAuth can expire, so permanent authorization is not promised. Native platforms without the Calendar plugin do not show an unsupported system-permission button.

Production inspection: RELOO_CALENDAR_CLIENT_ID and RELOO_CALENDAR_CLIENT_SECRET are absent. Google Calendar cannot be enabled without the project's Google OAuth client, consent configuration and approved callback. No credentials were invented or copied from unrelated integrations. Native source is changed; no claim of installed-device/iOS signing or permission-dialog verification on physical devices.

Mobile headers now name needs, neighborhood, article and calendar routes instead of generic RELOO. Search/area pages expose the existing location selector. On scroll, retained headers use the actual main page heading. News detail, informational documents, calendar setup and needs forms use a non-sticky compact header to preserve reading/form space. The selected location remains the existing store choice, not a GPS inference.

Loading uses lightweight CSS perspective, two dimensional rings, a three-face item and soft shadow, with reduced-motion static fallback and the existing screen-reader status. No percentage or success is simulated; existing request handling controls its lifetime.
