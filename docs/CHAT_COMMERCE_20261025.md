# RELOO conversational commerce — 25/10/2026

Before-change assessment: customer support widget, support API, grounded advisor and Messages entry. Rules 005–009, 011, 014–018, 020 and rental/payment domain controls apply. No new SDK, provider, tracking permission, asset or personal-data field. Existing support transcripts and opaque actor-bound session reference retain their current purpose and expiry (guest 7 days; account 30 days). No cross-user or guest-to-account transcript merge.

Journey: quick chat ↔ RELOO thread in Messages → describe need → refine actual public products → select product → existing rental date/quote/review flow → explicit customer request → owner confirmation → existing agreement/payment. AI cannot authorize a transaction, invent inventory, waive fees or confirm payment. Empty live inventory must remain empty.

Implementation uses one chat surface; rich cards and suggestions are restored from existing idempotency response records, owned and expiry-checked before reads. Context is recovered from the last response, rather than reset by the Messages URL. Product selection is a public listing ID, never a client price. Catalog read failures remain errors. Human takeover suppresses automatic replies.

Implemented: shared compact widget/embedded Messages surface; pinned RELOO thread entry; owner-bound latest-thread restoration; per-turn image/price/area rails, suggestions and actions restored from request records sharing the original transaction timestamp. No schema change or new public-schema privilege. Existing retention/purge covers the records. Switching products validates against the public catalog; no client-supplied price is accepted. Categories, supported area names and explicit budget limits are derived from recent customer turns. This bounded matcher is not a claim of unrestricted conversational understanding. Policies and explicit choices bypass the model round-trip.

Rental review reuses the actual RentalRequestFlow component, including server quote digest, identity checks, price-change review, idempotent inquiry, owner confirmation and subsequent agreement/payment. No parallel order engine. The chat keeps the form mounted when returning to the conversation, so its in-session selection remains. A signed-in customer must still explicitly send the request. Guest sign-in continuation uses the existing rental flow. Completed chat inquiries remain owner requests, not confirmed bookings or successful payments. Sale actions use the existing purchase route; stay/job modules retain their real availability restrictions.

Privacy information and existing contact consent/withdrawal are available in conversation options. First-use retention information remains visible by the composer. Invitations remain off by default and require the existing separate tab opt-in plus analytics/marketing consent; DNT/GPC respected. No credentials, transcript or new tracking data is placed in browser storage. Account and guest conversations are not silently merged.

Verification artifacts: `output/playwright/chat-commerce-20261025/` (synthetic browser flow and reviewed mobile screenshots), `output/uat/chat-commerce-20261025/` (technical checks/release report). Tests cover actual grounded advisor generation as well as UI; a browser interception fixture does not certify the production database, model, payment provider or device runtime. Real-device keyboard/safe-area and final production release require separate evidence. Production deployment is not implied by local implementation; source-bound Guardian evidence and applicable release authorization remain required.
