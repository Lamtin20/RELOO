# CRM central identity federation

Change assessment: authentication, CRM MFA, staging access and management entry points. Rules 005–009, 017–020 and existing role/security controls. Provider is the first-party CRM identity broker, not a new analytics or payment provider. New data: issuer/subject-to-local-profile mapping, one-time proof-key codes and expiring opaque sessions. No passwords, refresh tokens, production customer profiles or production roles are transferred to UAT. Mappings require explicit backend provisioning; signing in never creates a local administrator.

CRM verifies its existing GoTrue account, enabled staff access and real TOTP receipt. Target applications exchange a 30-second one-time code over an authenticated server channel, then receive an opaque upstream reference. Every authenticated target request rechecks that reference against CRM and rechecks local mapping/account/permissions. Local cookies are host-only, HttpOnly and Secure. Only local profile identity is returned to existing APIs; the remote authority does not override local business activation/KYC or permissions. A revoked CRM receipt or disabled mapping invalidates the next request.

Codes retain encrypted access JWTs only inside the central broker until expiry; they never contain a refresh token and are never sent to the browser as a JWT. Short-lived references expire at the earlier of the central JWT and MFA receipt. Target credentials are separate per allowlisted host. Requests with an unknown host, client, audience, verifier, mapping or expired authority fail closed. Return paths are local and validated.

This implementation is feature-flagged and must not be enabled until migration, explicit identity mapping, separate broker/client secrets, real MFA/revocation/replay tests and current release evidence are installed. Production remains subject to its existing Guardian gate. Account/customer federation beyond permitted CRM users is outside this initial scope. No legal approval is implied.

## Deployment contract

Central CRM: `RELOO_IDENTITY_MODE=broker`, existing `CRM_ORIGIN=https://crm.reloo.vn`, `APP_ORIGIN=https://reloo.vn`, plus distinct 32-byte hex `RELOO_IDENTITY_STAGING_SECRET`, `RELOO_IDENTITY_CHAT_SECRET`, `RELOO_IDENTITY_AGENT_SECRET` for enabled targets. Keep those values in protected server configuration, never browser config. Public production CRM must run the broker routes before a client is enabled.

Target application: `RELOO_IDENTITY_MODE=federated-client`, `RELOO_IDENTITY_ISSUER=https://crm.reloo.vn`, `RELOO_IDENTITY_TRANSPORT=private-bridge` and the matching per-host secrets. Preserve staging database, storage, noindex, outbound/payment limits and ordinary `CRM_ORIGIN=https://staging.reloo.vn`; the identity issuer is separate from the data environment. Configured staging hosts fail preflight if their broker secret or restricted transport is missing. Legacy local password/Bearer sessions do not bypass the central flow once enabled. Existing behavior is unchanged while the feature is off.

Staging networks are internal. `deploy/agent-office/compose.bridge.yml` adds a separate relay, not general egress for the application/agents. It accepts only POST to the three broker backchannel paths and GET/HEAD to two fixed RELOO health endpoints; all other routes are403. The relay strips incoming headers/cookies and supplies only required fixed Host/Content-Type/authorization headers. Public hops verify TLS certificates and SNI; IPv4 DNS avoids unavailable IPv6. No public ports, root filesystem read-only, UID101 and all capabilities dropped. The relay holds no identity client secrets itself. This explicitly authorized first-party transport is not a generic web proxy.

Apply `20261024180000_central_identity.sql` and existing security lockdown to both environments. Provision each mapping explicitly against an existing local profile; `enabled` defaults false, issuer/subject and issuer/local-profile are unique. No email-based account merging or role import is implemented. The reason and responsible operator must be recorded; do not treat a database insert as legal approval. Local CRM grants remain the source of page/action permissions. The operator must not invent a central subject or reviewer identity.

Endpoints: GET `/api/auth/federation/start`, `/authorize`, `/callback`; server-only authenticated POST `/exchange`, `/introspect`, `/revoke`. Central authorization reuses the existing Google/password/TOTP CRM flow. Entry pages automatically start a handoff when configured; explicit permission/expiry failures stop the redirect loop and offer a retry. Logout invalidates the central receipt used by the handoff and clears local identity/legacy management cookies. Other devices/receipts are not silently revoked.

WebSocket handshake and existing gated chat events resolve the same opaque identity in client mode. They cannot fall back to a supplied local bearer/profile ID. Existing account activation, identity expiry, thread membership and IP restrictions remain in force. The resolver is called again for gated events, so the broker is consulted again rather than trusting an indefinitely cached socket subject. Full live socket/Google federation acceptance remains NOT_TESTED.

Retention: codes expire after 30 seconds; browser state after 5 minutes; session references at the earlier of access-JWT and MFA expiry, at most 8 hours. The existing operations worker purges expired/revoked federation records when the feature is enabled. Mapping metadata lasts until unlink/account deletion and remains subject to the project's retention review. No background location, tracking SDK, customer transcript or hidden model reasoning is collected.

## Current verification boundary

Automated tests execute the migration in PostgreSQL-compatible PGlite and cover wrong client/verifier, replay, expiry, revoked MFA, disabled staff, denied public privileges and disabled-by-default mappings. Pure/backchannel tests cover issuer/audience/expiry, forged identity markers, encoded redirects, independent credentials, fixed HTTPS endpoints and response size. These do not certify live Google/TOTP federation. Broker deployment, explicit mapping and live cross-host acceptance remain NOT_TESTED until run with authorized accounts. No production deployment or mapping approval has been fabricated.
